# 算法侧与全栈侧责任边界

## 1. 算法侧负责

- ASR 输入规整和转写结果的来源标记；
- TTS 请求、音频取消和打断语义；
- 日常聊天与正式访谈的 `InterviewPolicy`、状态转移和问题数量约束；
- LLM 语义理解、`NarrativeCue`、`SemanticTurnProposal` 的候选合同；
- Memory 候选提取、连续原文来源校验、敏感性提示和诊断；
- 故事草稿、基础画像等派生任务的输入范围和失败隔离；
- HTTP 合同、版本字段、错误码、幂等、Fake/REAL_INTERNAL 运行方式；
- 固定案例、回放脚本、模型调用记录和算法质量评审。

## 2. 全栈负责

- 登录、家庭/社区角色、成员绑定和后端授权；
- 数据库、对象存储、队列、任务重试、监控和部署；
- 将接口事件呈现在访谈界面：文字、语音、等待、播放、打断、失败和恢复；
- Memory、故事、画像的页面展示、编辑入口和确认流程；
- 将 `opaqueSessionHandle`、`requestId`、幂等键和版本信息安全地传递；
- 正式 `CanonicalMemory` 的持久化实现、审计、撤回、删除和家庭权限执行；
- 生产环境的认证、限流、日志脱敏和回滚。

## 3. 产品负责人和团队负责

- 决定访谈是否自然、追问是否有价值、故事和画像是否可用；
- 决定哪些 Memory 需要老人确认、哪些敏感信息需要家庭或协作角色确认；
- 算法工程师先评估技术事实，产品/内容团队评估可用性，康养专家评估领域风险；
- 反馈必须标明角色和证据，不能把单次体验意见伪装成模型统计结论。

## 4. 接入评审门

全栈提交以下证据后，算法侧才把候选接口标为“接入完成”：

- 使用 Fake 完成主链和错误状态；
- 使用真实内部服务完成一次文字、一次语音、一次打断和一次 `view`；
- 页面没有暴露密钥、provider 原始错误或内部权限字段；
- Memory 候选、故事、画像和 Shadow 的状态显示准确；
- 重复请求、超时、旧版本结果和会话结束均有可验证处理；
- 生产 `CanonicalMemory` 写入仍由授权后端控制，不能由浏览器或 LLM 直接触发。
