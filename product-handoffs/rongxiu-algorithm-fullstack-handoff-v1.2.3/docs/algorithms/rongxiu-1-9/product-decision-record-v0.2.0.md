## 2. 业务对象解释

### 2.1 总信

总信是多人分别提交回忆、感谢或祝福后，由有效统筹从已批准素材中组织成的一封面向荣休者的集体信。

它不是单个人的祝福润色，也不是多人内容的简单拼接。模型负责生成正文候选；称谓、结尾模板、正式署名、来源核对和发布由产品/统筹流程管理。

总信生成允许按主题重排素材，但不能凭空制造时间顺序、因果关系、集体授权或“全体同事”的代表性。

### 2.2 邀请寄语

本期 07 的主分支是礼前邀请亲友参与荣休礼共创、投稿或提供素材。结构化字段（活动信息、链接、截止时间等）由模板管理；如果用户已有自然语言草稿，AI 只负责润色草稿。

邀请荣休者查看或接收礼物属于另一个业务分支，暂不与本期共创邀请混用，后续需要单独入口、渠道和验收。

### 2.3 祝福空输入起笔

08 出现在参与者填写个人祝福但尚未写出正文的页面。首期使用静态起笔模板，不调用模型，不生成完整祝福。用户已有实质祝福时，进入 04 祝福润色。

### 2.4 总信局部编辑

09 处理已经生成的总信候选，由有效统筹选择段落或文字并提出编辑指令。编辑结果是新 candidate/new revision，不能覆盖冻结版本；非选区、署名、来源、争议提示和 AI 标识由后端保护。

## 3. 已冻结的产品边界

- 1、2、3、4、5、6、9 是 AI 候选能力；7 的结构化部分由模板负责；8 不建设 AI 模型路由。
- 02 首期只处理已有文字描述或确认后的文字，不读取图片像素；像素分类、照片成故事另行建设。
- 05 只有作者确认用途且有效统筹逐条批准的素材才能进入总信模型输入。
- 05 中“素材类型”和“叙述归属”是两个维度；作者身份不能证明谁亲历。每条素材均有独立匿名定位标记。
- 05 模型不生成正式称谓、结尾模板或正式署名；集体署名必须来自实际授权联名。
- 07 主分支是礼前邀请亲友共创投稿，AI 不根据空白输入生成完整邀请。
- 07 普通共创入口允许转发；登录、身份关系确认和投稿审核仍然生效，转发不授予管理权。
- 08 静态起笔模板只服务个人祝福空白页，点击后形成可编辑草稿，不自动提交。
- 09 由有效统筹进行选段/选中文字编辑，采用和撤销都会生成新 revision，并使旧确认失效。
- 不自动跨项目使用长期 Memory；当前项目复用必须显式选择且权限仍有效。
- 待审稿不得进入总信生成；受礼者不查看内部审批日志和未确认候选。

## 4. R1～R5 已决策实施口径

### R1：05 匿名来源与叙述归属

后端业务对象采用以下严格结构；送模型前必须移除 `sourceRef`：

```json
{
  "sourceType": "STORY",
  "sourceRef": "backend-only-reference",
  "authorLabel": "投稿者A",
  "materialLabel": "素材A-01",
  "narrativeAttribution": {
    "experienceSubject": "AUTHOR",
    "basis": "FIRSTHAND"
  },
  "text": "已获准素材"
}
```

- `sourceType`: `STORY | WISH | CAPTION`。
- `experienceSubject`: `AUTHOR | RECIPIENT | THIRD_PARTY | UNKNOWN`。
- `basis`: `FIRSTHAND | REPORTED | OPINION_OR_WISH | UNKNOWN`。
- 可选匿名字段为 `speakerLabel`、`experiencerLabel`。
- `sourceType` 表示素材类型，`narrativeAttribution` 表示谁讲、谁亲历以及依据，两者不能合并成一个枚举。
- `authorLabel` 在项目内按作者稳定；同一作者的每条素材使用唯一 `materialLabel`，以便准确回溯。
- 统筹审核页显示匿名标签；有权限的统筹可由后端映射查看原素材。最终正文不显示这些内部标签。
- 真实账号、手机号、审批记录、内部来源 ID 和映射关系只留后端。匿名标签不等于正文已经脱敏，输入正文仍须按规则处理。
- 后端必须权威复核用途、审批、revision 和权限，不能信任客户端传入的“已批准”声明。

### R2：05 总信风格字段与交互

| `style` | 前端名称 |
|---|---|
| `natural_oral` | 自然口述 |
| `soft_literary` | 文辞柔美 |
| `calm_dignified` | 沉静大气 |
| `formal_sincere` | 郑重真诚 |

- 风格控件默认可见，预选“自然口述”；统筹可直接生成，无须先操作控件。
- 每个选项保留说明以及同一素材的对照示例，名称不得替换成同义词。
- 新接口统一使用 `style`；缺省时由后端补为 `natural_oral`，不能依赖 JSON Schema 的 `default` 自动写值。
- 旧 `tone` 只在兼容层处理；映射须由算法核对真实旧值，不能猜测旧枚举含义。
- 换风格重新生成时保留已有人工修改稿；新结果先预览，采用后重新确认。
- 总信页面只有“生成总信”一个主要任务时，不增加只有一个选项的“加工动作”下拉框。

### R3：07 共创邀请入口、分享与准入

- 入口位于统筹项目主页的“邀请亲友共创”；项目发起完成后仍可进入，项目名称和截止日期复用已有资料。
- 系统先生成固定邀请模板；只有统筹已有寄语草稿时，才允许选择 AI 润色。
- 统筹预览后主动分享；支持微信好友/群分享和二维码海报，复制链接按实际渠道能力开放。
- 支持面向多人邀请，但不读取通讯录，也不自动逐人或群发。
- 首期允许转发普通共创入口。新进入者仍须登录、确认身份关系并经过投稿审核；转发不授予管理权，也不能读取他人私密投稿。
- 若未来要求仅指定受邀者投稿，另建账号绑定邀请或准入审核，不能只靠前端禁止转发。
- 分享按钮点击不等于送达；可以统计有效进入、参与和投稿，不能据此显示“已送达”。
- “邀请荣休者查看/接收礼物”作为后续独立分支，不复用本期路由。

### R4：08 静态起笔模板与轮换

首期准备 6 条通用起笔，每批展示 3 条，`batchIndex=0|1`，支持“换一批”：

1. 想借这个机会，对您说……
2. 送上这份祝福，愿您……
3. 关于接下来的生活，我想祝您……
4. 此刻最想送给您的一句话是……
5. 有一份心意，想这样告诉您……
6. 写下这段话，我想表达的是……

- 仅在正文为空或只有称呼时展示；点击模板时重新检查正文，防止覆盖并发输入。
- 点击后只把模板填入可编辑草稿，不自动提交；换一批不能修改已经写好的内容。
- 用户补充实际表达后才能进入 04 润色；纯模板或只改标点不算实质内容。
- 首期不按关系维护多套模板，不长期记录个人看过哪条，不新增 HTTP 模型接口。
- 后三条是基于已批准中性原则补齐的实施文案，不表示产品逐字回传。

### R5：AI-D04 留存、删除与撤回建议基线

| 数据 | 建议口径 |
|---|---|
| 未采用候选 | 最后活动后 7 天清理；明确删除时立即退出可用范围 |
| 临时转写音频 | 确认后尽快删除；失败恢复最长 24 小时 |
| 原声祝福、明确保存的录音 | 作为用户原件，不按临时转写音频删除 |
| 用户原件 | 按有效业务用途保存；普通删除提供 30 天恢复期，期间禁止展示、生成或分享 |
| 审计元数据 | 180 天，默认不含正文、音频和私信全文 |
| 已采用成品 | 随有效业务用途保存，仍受来源撤回影响 |

- 撤回后立即停止采用、展示或分享已失去对应用途许可的候选和成品，并清理相关索引；无关内容不整体失效。
- 所有实际送入模型的素材都要登记依赖，即使成品没有直接引用其文字。
- 第三方删除失败可重试，只保留必要的删除任务标识和状态；不能因此无限保留本地正文副本，未确认完成时不得显示“已全部删除”。
- 离线设备重新联网时，先处理撤回，再恢复内容访问。
- 真实期限、第三方/备份/离线删除能力和离线许可有效期必须经过 AI-D04 技术冻结和上线验收，不能把以上建议直接写成已实现的生产承诺。

### 09 局部编辑的已冻结技术口径

- 请求必填 `letterText`、`instruction`、`letterRevision`、`inputHash`、`selection`、`protectedRanges`、`approvedFacts`。
- `selection` 为 `{start,end,selectedText}`；`protectedRanges` 为 `{start,end,kind}` 数组，`kind` 仅允许 `SIGNATURE | SOURCE | DISPUTE_NOTICE | AI_LABEL`。
- 索引按原字符串 Unicode code point、左闭右开计算；校验前不做 NFC、trim 或换行转换。选区必须非空、边界有效、`selectedText` 与原文一致，且不能和保护区相交。
- 模型只输出完整 `{"text":"..."}`。后端逐字比较原前缀和后缀；候选长度变化时不能使用旧绝对坐标截取后缀。非选区的空格或换行变化也返回 `PROTECTED_CONTENT_CHANGED`。
- 生成只产生 candidate；采用和撤销都生成新 revision，旧确认失效。撤销不能恢复已经撤回的素材许可。
- 生成前和采用时都要重查权限、revision、inputHash 和用途许可。

## 5. 对算法和全栈的直接影响

1. 08 从生产 Provider 路由表中移除，保留静态模板配置，不建设模型调用。
2. 07 只保留 `polish` AI 分支；`starter` 不作为本期模型路由，结构化信息由模板字段管理。
3. 05 的新接口只使用小写 `style` 枚举；后端负责补缺省值，旧 `tone` 仅由兼容层按真实历史值映射。
4. 05 的模型输入使用 `sourceType + authorLabel + materialLabel + narrativeAttribution + text`，并在调用模型前移除 `sourceRef`；真实身份和审批元数据只留后端。
5. 09 的编辑权限固定为有效统筹；Unicode code point 选区、保护区逐字比较、revision/inputHash、旧确认失效、撤销和用途复核都是全栈门禁。
6. 10 的 Memory 策略按角色和当前项目隔离；待审稿不得进入 05 模型输入。
7. 07 的主业务场景固定为礼前邀请亲友共创投稿；分享渠道不等同送达，转发不绕过登录、身份关系和投稿审核。
8. 所有进入 05/09 模型输入的素材建立依赖记录；素材用途撤回后按依赖停止对应候选和成品继续使用。

## 6. 上线前仍须验证的内容

- 产品回复不等于 Provider 已接入；
- Prompt 和产品决策确认不等于模型效果通过；

- 09 已冻结数据和校验规则，仍需全栈完成选区保护、逐字差异比较、revision 冲突、采用/撤销和用途撤回测试。
