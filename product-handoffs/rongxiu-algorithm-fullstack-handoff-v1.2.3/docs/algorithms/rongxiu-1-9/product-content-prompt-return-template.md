# 产品与内容：Prompt 回传模板

> 版本：`v1.2.3-frozen-handoff`
>
> 用途：产品/内容同事调好文案后，把最终 Prompt 交回算法端。
> 默认交付：模型能力提交 `System Prompt` + `User Prompt`；08 提交静态模板版本和文案。不要求产品提交 Workflow、Schema、模型参数或 DSL。

## 一、正常情况下只需要填这一张表

| 能力编号/名称 | Prompt 版本 | System Prompt 文件或正文 | User Prompt 文件或正文 | 本次主要调整 | 调整目的 | 产品/内容负责人 | 日期 |
|---|---|---|---|---|---|---|---|
| 示例：04 祝福润色 | `wish-polish-v1.2.0` | `04-wish-polish.md` 的 System Prompt，或粘贴最终正文 | `04-wish-polish.md` 的 User Prompt，或粘贴最终正文 | 语气更温暖，减少书面词 | 更适合目标用户阅读 | 张三 | 2026-10-13 |
|  |  |  |  |  |  |  |  |

如果没有修改 Prompt 以外的内容，到这里就可以回传。System Prompt 和 User Prompt 请分别标明，不要把两段合成一段让算法端猜用途。

08 没有 System/User Prompt。若产品调整静态起笔，只需在第二张表登记 `templateVersion`、6 条最终文案、展示批次和调整原因。

建议直接粘贴最终 Prompt 正文；如果以文件提交，请保证文件与本表一起交付，不要只写“见原文”。

## 二、只有改了 Prompt 以外的内容时，才填写这张表

下列两行是 v1.2.3 已确认内容的填写范例，不是当前待决策项。后续若提出新变更，应另起一行并明确标为“变更提案”。

| 能力编号/名称 | 改动位置 | 改动前 | 改动后 | 为什么要改 | 是否改变输入字段/含义 | 是否改变输出格式 | 是否改变产品流程或按钮 | 是否涉及安全、隐私、确认或 Memory | 需要谁确认 | 状态 |
|---|---|---|---|---|---|---|---|---|---|---|
| 已确认示例：07 邀请寄语 | 产品流程与入口 | 空白输入直接生成，入口和准入未明确 | 统筹从项目主页进入；固定模板先行，只有已有寄语草稿时才可选 AI 润色；普通共创入口可转发，但仍需登录、确认身份关系并经过投稿审核 | 固定礼前共创定位，避免把分享误当送达或管理授权 | 是：AI 仅接收已有草稿 | 否 | 是 | 是：准入、投稿审核与私密内容权限 | 产品 + 算法 + 全栈 | 已确认（v1.2.3） |

## 三、回传前自查

- [ ] System Prompt 和 User Prompt 已分开；
- [ ] 已填写 Prompt 版本、负责人和日期；
- [ ] 没有把人名、时间、地点或经历写成输入中不存在的事实；
- [ ] 没有把“候选文案”描述成已经发送或已经写入正式内容；
- [ ] 如果改了输入字段、输出格式、按钮流程、确认规则、隐私范围或 Memory，已经填写第二张表；
- [ ] 没有粘贴 API Key、Token、密码或含凭据的链接。

## 四、产品/内容不需要填写的内容

以下内容由算法和全栈接手，不是本次产品/内容交付的必填项：

- Provider/App ID、Workflow ID 和部署配置；如选择 Dify，DSL 由全栈自行维护；
- provider、model、temperature、top_p、max tokens；
- JSON Schema、后端错误码和数据库字段；
- candidate 写入、确认、应用、撤销和长期 Memory；
- API Key、服务端 URL 和部署信息。

如果产品只是想快速预览，可以使用 Dify 的 `Start/User Input → LLM → Output`，也可以使用其他模型平台或本地测试脚本；不需要自行搭生产级 Code、IF/ELSE、后端 HTTP Tool 或复杂 Agent。

## 五、Prompt 回传后，技术侧还要完成什么

| 阶段 | 负责人 | 需要完成的事 | 通过标准 |
|---|---|---|---|
| Prompt 接收 | 算法 | 核对 System/User Prompt、版本和事实边界 | Prompt 可审查，未改变未授权事实规则 |
| 契约冻结 | 算法 + 全栈 | 对齐 `purpose + mode`、输入字段、输出 `text/candidate` 和错误语义 | 全栈不需要猜字段含义或失败处理 |
| Provider 接入 | 全栈 | 服务端调用模型 Provider（可选 Dify），配置密钥、路由、超时、重试、取消和日志 | 前端拿不到密钥，成功和失败均有稳定结果 |
| 产品闭环 | 全栈 + 产品 | 展示原文和候选，支持确认、拒绝、应用、撤销 | 生成结果不会直接覆盖正式内容 |
| 真实验收 | 算法 + 全栈 + 产品 | 跑正常、空值、超长、注入、敏感信息和失败场景 | 通过自动化和人工验收后，才能称为产品可用 |

所以，“产品/内容只回传 Prompt”是正确的职责边界，但它只是技术接入的输入，不是产品可用性的证明。

全栈从 `PROMPT_RECEIVED` 推进到 `RELEASE_READY` 的条件见 [`fullstack-acceptance-boundary.md`](./fullstack-acceptance-boundary.md)。
