# 荣休礼 1～9：全栈验收边界

> 交付版本：`v1.2.3-frozen-handoff`
>
> 这份文件与 [`00-product-reading-guide.md`](./00-product-reading-guide.md)、[`product-content-prompt-return-template.md`](./product-content-prompt-return-template.md) 配套使用。

## 先给结论

产品和内容同事只需要回传模型能力最终的 **System Prompt + User Prompt**，并注明 `purpose`、`mode`、Prompt 版本、调整说明、负责人和日期；08 回传静态模板版本和文案。这样足够让算法/全栈开始接入，但**不能单独证明产品已经可以正常运行**。

从 Prompt 回传到产品可用，中间还必须由算法/全栈完成契约冻结、Provider 接入、候选内容闭环、权限与隐私保护、自动化测试、目标环境验证和产品验收。Prompt 只是技术接入的输入；完整验收以本文件的状态门禁为准。

## 1. 责任边界

| 参与方 | 必须交付 | 不要求承担 |
|---|---|---|
| 产品/内容 | 模型能力的最终 System/User Prompt；08 的静态模板版本和文案；`purpose + mode`、版本、主要调整、调整目的、负责人、日期 | Provider、App/资源 ID、模型参数、Schema、部署配置、后端接口、数据库、候选确认/撤销、发布和密钥配置 |
| 算法 | Prompt 事实边界与版本审查、输入/输出合同、fixture 与断言、能力门禁、模型效果风险说明 | 替产品决定入口、按钮和用户体验 |
| 全栈 | 服务端 Provider、路由、超时/重试/取消/幂等、候选保存与确认/应用/撤销、权限、日志、部署和运行验收 | 擅自改变 Prompt 事实边界或用 UI 行为替代后端安全控制 |
| 产品 + 算法 + 全栈 | 共同确认契约变更和最终产品验收 | 把未完成的技术或体验门禁标为上线 |

如果只修改 Prompt，产品只填回传模板第一张表即可。只有修改输入字段、输出结构、按钮流程、确认规则、隐私范围或 Memory 时，才填第二张表。

## 2. 技术侧接收的最小材料

算法/全栈从产品收到以下内容后可以开始工作：

1. 每个模型能力的最终 System Prompt 和 User Prompt，且两者分开；08 提供静态模板版本和文案；
2. `purpose`、`mode` 和完整 `promptVersion`；
3. 主要调整和调整目的，便于回归时解释变化；
4. 负责人和日期，便于追溯；
5. 如有 Prompt 之外改动，附回传模板第二张表和共同确认状态。

输入 Schema、成功响应 `{"text":"..."}`、错误语义、候选确认规则、`revision/inputHash` 和敏感信息策略沿用本目录已有契约，由算法/全栈核对，不要求产品重新填写或设计。

## 3. 验收状态与通过条件

状态只能按顺序推进；前一个状态没有证据，不能跳到后一个状态。

| 状态 | 负责方 | 必须完成 | 证据 | 可以对外怎么说 |
|---|---|---|---|---|
| `PROMPT_RECEIVED` | 产品 → 算法 | Prompt 对、版本和回传记录完整，System/User 没有混在一起 | 回传表、Prompt 快照、版本记录 | 已收到 Prompt |
| `CONTRACT_FROZEN` | 算法 + 全栈 | `purpose + mode`、输入字段、输出 `text/candidate`、错误语义和版本映射已冻结 | Schema、路由表、契约评审记录 | 可以开始技术接入 |
| `PROVIDER_INTEGRATED` | 全栈 | 由服务端调用模型 Provider（可选 Dify）；密钥、超时、重试、取消、幂等和日志已接入 | Provider 配置摘要、脱敏调用记录、错误映射测试 | 已完成 Provider 接入 |
| `CANDIDATE_LOOP_VERIFIED` | 全栈 + 算法 | 成功只生成 candidate；确认、拒绝、应用、撤销和 revision/hash 规则可复现 | 自动化测试、数据库/接口记录、冲突测试 | 候选闭环已验证 |
| `PRODUCT_ACCEPTED` | 产品 + 算法 + 全栈 | 目标环境中的界面、提示、失败恢复和目标用户阅读体验通过人工验收 | 验收清单、截图或录屏索引、问题关闭记录 | 产品验收通过 |
| `RELEASE_READY` | 负责人 | 前述门禁全部通过，发布配置和回滚方式明确，未完成能力仍标记阻塞 | 发布检查单、版本/回滚记录 | 可以进入发布流程 |

“产品只回传 Prompt”最多支持达到 `PROMPT_RECEIVED`；它不会自动把状态推进到 `PROVIDER_INTEGRATED`、`PRODUCT_ACCEPTED` 或 `RELEASE_READY`。

## 4. 全栈必须验收的六个方面

### A. 接口和路由

- 请求通过服务端进入 `AssistantProvider`，前端、小程序和相框不持有 Provider URL 或 App Key；
- 使用唯一的 `purpose + mode` 路由，未支持的能力返回稳定错误；
- `promptVersion`、`traceId/requestId`、模型版本和耗时可以关联查询；
- 请求只携带完成任务所需的最小字段，不把完整用户目录、设备令牌或未授权原文直接转发。

### B. Provider 和运行恢复

- 正常响应必须能解析为约定的对象，并校验 `text` 非空、长度和禁止字段；
- 超时、限流、401/403/404/5xx、非法 JSON、空输出、取消和模型失败都有稳定业务错误；
- 重试有上限且不会重复写入；取消会停止或忽略过期响应；
- Provider/模型密钥只在服务端 secret storage 中配置，日志不能打印密钥、完整敏感原文或可还原的凭据。

### C. 候选内容闭环

- Provider 只产生候选，不直接改正式内容；
- 用户确认前可以查看、拒绝或重新生成；确认后才允许应用；
- 应用、撤销和恢复有清晰的 revision 规则；原文变更时返回 `REVISION_CONFLICT`，不能用旧候选覆盖新内容；
- 涉及长期 Memory、敏感健康/家庭/财务信息时，必须经过明确授权和后端 Policy Gate。

### D. 安全和事实边界

- 素材中的“忽略前面规则”等内容只能作为素材处理，不能覆盖 System Prompt；
- 模型不得补造输入未提供的人名、时间、地点、经历、关系或承诺；
- 前端不能绕过服务端权限、确认和审计；
- 发生 Provider 失败或校验失败时保留原文，不把空结果当成功。

### E. 自动化和目标环境验证

每个已接入能力至少覆盖：

1. 正常最小输入；
2. 空输入、超长输入、字段类型错误；
3. Prompt Injection 文本；
4. 手机号、地址、令牌或其他敏感内容；
5. Provider 超时、限流、认证失败和 5xx；
6. 非法 JSON、空文本、超长输出；
7. 取消、重试、幂等和 revision conflict；
8. 候选未确认时不得写入正式内容或长期 Memory。

测试必须在目标 Provider/目标环境重新运行；本地 fixture 通过不等于目标 Provider 已经发布，也不等于真实用户效果已验证。

### F. 产品人工验收

产品需要检查：入口是否清楚、输入和候选是否容易区分、等待/失败/重试提示是否能理解、确认/撤销路径是否可找到、长文本和目标用户阅读体验是否合适。人工验收通过后才能进入 `PRODUCT_ACCEPTED`，不能用接口 200、调试平台能运行或单个示例看起来不错来替代。

## 5. 1～9 的接入起点与剩余门禁

| 能力 | Prompt 回传后可以开始 | 仍需完成的技术/产品门禁 |
|---:|---|---|
| 1 人物介绍整理 | 契约冻结、Provider stub 和基础回归 | 真实 Provider、候选确认和产品人工验收 |
| 2 照片描述整理 | 文字描述链路和 Provider stub | 图片理解是否接入另行设计；不能把文字版验收说成图片能力 |
| 3 故事正文整理 | 文本链路和 Provider stub | 正文 `revision` 校验、候选应用和冲突恢复 |
| 4 祝福润色 | 文本链路和 Provider stub | 事实/称呼保护、候选确认和产品验收 |
| 5 总信首次生成 | 按已冻结的匿名素材投影、四风格和 candidate 链路实现 | 待审稿不得入模；审核页的后端来源映射、依赖记录和撤回传播必须验收 |
| 6 礼后问候整理 | 文本链路和 Provider stub | 活动事实边界、失败恢复和产品验收 |
| 7 邀请寄语 | 固定模板和 `polish` 草稿链路可实现 | 分享渠道能力、登录/关系确认、投稿审核、进入/参与/投稿统计须按目标端验收；分享点击不得显示已送达 |
| 8 祝福空输入起笔 | 6 条静态模板和两批轮换可直接实现 | 空白重查、防覆盖和点击填入行为须验收；不得配置模型路由 |
| 9 总信局部编辑 | 按已冻结的选区、保护区、revision/hash 和 candidate 契约实现 | 权限重查、逐字非选区比较、旧确认失效、撤销及来源许可撤回传播须验收 |

## 6. 证据清单与不可越过的声明边界

全栈交付给集成负责人时，应至少附上：

- Prompt 快照、版本和契约映射；
- 请求/响应 Schema、路由和稳定错误码；
- Provider 配置摘要（只写 secret storage 配置名，不写 Key）；
- 自动化测试结果和失败用例处理；
- 目标环境调用记录（脱敏，保留 requestId、promptVersion、输入 hash、耗时和状态）；
- 候选确认、应用、撤销、冲突恢复记录；
- 产品人工验收记录、未完成门禁和回滚方式。

以下说法不能互相替代：

| 已有证据 | 不能因此声称 |
|---|---|
| 产品交回 Prompt | Provider 已接入或产品已上线 |
| 任意调试平台单次运行成功 | 生产接口、权限、候选闭环和失败恢复已通过 |
| 接口返回 200 | 输出事实正确、目标用户体验可用或可写入正式内容 |
| 自动化 fixture 通过 | 真实家庭数据准确率、稳定性或生产质量已证明 |
| 本地文档和部署配置完整 | 目标 Provider 已接入、发布并具备运行依赖 |

当前交付包不包含目标 Provider 的 App/资源、Key、发布状态或真实用户验收结果；这些要由算法/全栈在目标环境完成并留下证据。

R5 的留存期限是产品建议基线。第三方删除、备份清理、离线设备重连先处理撤回以及离线许可有效期属于 `AI-D04` 上线门禁；未取得目标环境证据前，不能把建议期限写成已实现的生产承诺。
